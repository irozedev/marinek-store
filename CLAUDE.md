# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`marinek.store` — одностраничный лендинг марафона похудения для женщин (укр. язык) + юридические страницы + страница «дякуємо» после оплаты. Next.js 14 (App Router), TypeScript, Tailwind CSS.

**Критично: сайт полностью статический (`output: 'export'` в [next.config.mjs](next.config.mjs))**. Это значит:
- Next.js API-роуты (`route.ts`) **не работают** — сервера нет вообще, всё собирается в статические файлы в `out/`.
- Любая серверная логика (webhook-и, проверка платежей, генерация чего-либо на лету) должна жить **вне** этого Next.js-приложения — например, как Netlify Functions в том же Netlify-сайте (см. ниже).
- `images: { unoptimized: true }` — нет серверной оптимизации картинок, все фото заранее сжаты в WebP (`public/images/`).

## Хостинг и деплой

- **Netlify** ([netlify.toml](netlify.toml)): `command = "npm run build"`, `publish = "out"`.
- Значения `NEXT_PUBLIC_*` вшиваются в билд на этапе сборки — после смены env-переменных нужен **ребилд**, а не просто рестарт.
- Домен: `marinek.store`.

## Оплата и выдача доступа (переделано 25.07.2026)

До этого доступ раздавался одной статичной ссылкой на всех, вшитой в клиентский бандл: `/thank-you?plan=X` открывался кем угодно без оплаты, а инвайт расходился пересылкой. Сейчас платёж создаётся на нашей стороне, подтверждается подписанным вебхуком, и только после этого выпускается персональный одноразовый инвайт.

**Готовые «платіжні кнопки» WayForPay удалены** из кабинета — они не позволяли задать свой `orderReference`, то есть связать платёж с человеком. Вместо них Purchase API: поля собираются и подписываются на сервере, клиент сабмитит форму на `secure.wayforpay.com/pay`.

Поток целиком:

```
Tariffs.tsx → PayButton → POST /api/create-payment
   ↓ (создаётся заказ pending, цена из СЕРВЕРНОГО прайса)
форма → secure.wayforpay.com/pay
   ↓ оплата
serviceUrl → /api/wayforpay-callback   (проверка подписи → paid → инвайт → письмо)
returnUrl  → /api/payment-return/<токен> → 303 → /thank-you/?t=<токен>
   ↓
/thank-you — статическая страница «ссылка у вас на почте»
```

**Доступ выдаёт только письмо.** `/thank-you` ссылку не показывает, и
`/api/get-invite` её больше не отдаёт — иначе она читалась бы в devtools у
любого, кому досталась ссылка на страницу с токеном. Инвайт одноразовый и
живёт 7 дней, а адрес страницы легко переживает владельца: вкладка, история,
чужой компьютер. Почта привязана к человеку, страница — нет.

Сама страница (04.08.2026) стала **статической, без запросов**: раз токен до
неё не доезжает, опрос статуса, экраны «оплата не прошла» / «деньги возвращены»
и карточка «заказ не найден» были кодом, который в реальном потоке не
выполнялся никогда. Хуже: без токена женщина, только что заплатившая, видела
именно «не знайшли ваше замовлення».

Функции в [netlify/functions/](netlify/functions/), общий код в [netlify/lib/](netlify/lib/). Next.js API-роуты не работают — сайт статический.

### Грабли, на которые уже наступили

**Цена только с сервера** ([netlify/lib/plans.ts](netlify/lib/plans.ts)). Если брать из тела запроса, можно оплатить `personal` за 1 единицу валюты.

**Сумму сверять с заказом даже при валидной подписи.** Подпись подтверждает лишь то, что запрос от WayForPay.

**Вебхук обязан быть идемпотентным.** WayForPay ретраит до 4 суток, пока не получит подписанный `accept`. Без замка каждый ретрай выпускал бы новый действующий инвайт — в `issueInvite` для этого условный UPDATE по `invite_issued_at`.

**Отвечать `accept` даже если Telegram или почта упали** — иначе вебхук ходит днями. Заказ останется `paid` без `invite_link`, это видно в базе.

**Что документация WayForPay реально говорит про возврат** (сверено 04.08.2026):

- **Отдельного `declineUrl` в Purchase API нет.** Отказ некуда отправить своим адресом — развести успех и неудачу можно только у себя. Комментарий в `/payment-failed` про «WayForPay declinedUrl» вводил в заблуждение.
- На `returnUrl` браузер возвращается **методом POST**, в теле — результат платежа.
- **Тело подписано той же HMAC_MD5, что и вебхук**: `merchantAccount;orderReference;amount;currency;authCode;cardPan;transactionStatus;reasonCode`. Их собственный плагин для WooCommerce эту подпись проверяет. Значит `transactionStatus` с возврата можно доверять — если подпись сошлась.
- Полного списка значений `transactionStatus` в документации нет; подтверждены `Approved`, `Declined`, `Refunded`.

Отсюда три уровня доверия в [payment-return](netlify/functions/payment-return.ts), от надёжного к слабому: подпись сошлась → верим статусу в обе стороны; подписи нет → смотрим статус заказа в базе (его ставит подписанный вебхук); ничего не опознали → ведём на `/thank-you`, чей текст не врёт и при неудачной оплате. Неподписанному телу верим **только в сторону отказа** — иначе кто угодно прислал бы `transactionStatus=Approved`.

**Токен возврата — В ПУТИ, не в query.** WayForPay режет query-строку у `returnUrl`; проверено живым платежом — женщина видела нашу же страницу «Сторінку не знайдено», то есть запрос доходил, а `?t=` исчезал. Плюс WayForPay возвращает браузер **методом POST**, а Netlify на POST к статике отдаёт 404 — поэтому возврат принимает функция и делает 303 (этот статус превращает POST в GET).

**Логи функций Netlify через CLI приходят с пустым сообщением** — видно только время и `INFO`. Диагностировать ими не выйдет, не тратьте время.

## Telegram — три тарифа, ДВА канала

```
standard          → TG_CHANNEL_STANDARD_ID   «МАРАФОН СХУДНЕННЯ WITH MARINEK 💪»
chat, personal    → TG_CHANNEL_PREMIUM_ID    «VIP СХУДНЕННЯ WITH MARINEK💪»
```

Инвайты выпускаются `createChatInviteLink` с `member_limit: 1` и сроком 7 дней — ссылка умирает после первого входа. `member_limit` и `creates_join_request` взаимоисключающие, поэтому прежние «Заявки на вступ» больше не используются.

Бот `@marinek_marathon_bot` — админ в обоих каналах **только с правом «Додавати підписників»** (`can_invite_users`). Больше прав не давать: токен лежит в env, и утечка не должна давать возможность снести канал.

**Возврат денег гасит инвайт** (`Refunded`/`Voided` → `revokeChatInviteLink`). Ограничение: если женщина уже вошла в канал, отзыв ссылки её оттуда не выгоняет — для этого нужно знать её Telegram-аккаунт, то есть подписка на `chat_member` и хранение участников. Пока такие случаи разбираются вручную.

Ссылка приходит **только письмом** через Resend (04.08.2026 её убрали и со страницы, и из `/api/get-invite`). Отсюда следует, что письмо — не страховка, а единственный канал: если Resend не ответил, у покупательницы не остаётся ни одного пути. Такие заказы видны в базе точно — `invite_link` заполнен, `email_sent_at` пустой; это и есть список на ручную досылку через `reissue-invite`.

Раньше на странице ссылка показывалась тремя слоями (кнопка `https://t.me/+HASH`, `tg://join?invite=HASH` на случай блокировки домена `t.me`, и текст с кнопкой «скопіювати»). Если возврат на страницу когда-нибудь заработает и ссылку решат вернуть — эти три слоя нужны снова, поодиночке каждый ломается.

## Структура

```
src/
  app/            # роуты (App Router): /, /oferta, /privacy, /rules,
                  # /thank-you, /payment-failed, /admin
  components/     # секции лендинга, LegalLayout, CookieConsent, ThankYouCard,
                  # PayButton, ResendInviteForm, admin/
  lib/site.ts     # START_DATE, GA, RESULTS — БЕЗ цен и инвайтов, они на сервере
netlify/
  functions/      # create-payment, wayforpay-callback, get-invite, payment-return,
                  # reissue-invite, resend-invite, publish-site
  lib/            # wayforpay (подписи), telegram, plans (прайс), db, email
scripts/
  sync-content.mjs  # забирает контент из Supabase ПЕРЕД сборкой
db/               # миграции SQL — накатываются вручную в SQL Editor
docs/             # разовые настройки инфраструктуры
```

Всё, что попадает в `src/`, видно в исходниках страницы. Цены, платёжные ссылки и инвайты живут только в `netlify/` — именно через `src/lib/site.ts` они раньше и утекали.

Дата старта потока и карточки результатов приходят в `src/lib/site.ts` из `content.generated.json`, который перед каждой сборкой пишет `scripts/sync-content.mjs`. Этого файла в гите нет намеренно: источник правды — база, которую редактирует Марина. Запасной вариант на случай недоступной базы — `src/lib/content.defaults.json`, он в гите вместе с фотографиями.

`START_DATE` по-прежнему одна константа: встречается в hero, тарифах, финальном CTA, sticky CTA и `<title>`. Дата переносилась уже трижды — теперь меняется из `/admin`, руками в коде трогать не нужно.

## Админка `/admin` — редактор контента

Марина меняет дату старта и карточки «Результати учасниць». Разовые настройки (SQL, аккаунт, build hook) — [docs/admin-setup.md](docs/admin-setup.md).

```
/admin (статика) → Supabase напрямую под её входом → правки лежат в базе
       ↓ «Опублікувати»
/api/publish-site → проверяет её токен → build hook Netlify
       ↓ сборка
scripts/sync-content.mjs: дата и фото из Supabase → public/uploads → next build
```

**Сайт остаётся статическим.** Контент читается **при сборке**, а не из браузера. Рантайм-фетч отвергнут: дата стоит в первом экране, фото участниц — тоже выше сгиба, и то и другое мигало бы при загрузке. Плюс лендинг перестал бы открываться, когда Supabase лежит.

**Фото выкачиваются, а не линкуются** на Supabase Storage: иначе каждое фото — лишний домен в критическом пути и зависимость от того, не заснул ли бесплатный проект. После выкачки их раздаёт CDN Netlify. Bucket поэтому приватный — публичный доступ не нужен.

**Правки не попадают на сайт сразу, и это главный предохранитель.** Пока не нажата «Опублікувати», живой сайт не меняется вообще — значит, из кабинета его нельзя сломать в принципе, а ошибку видно и можно исправить до публикации.

**Что мешает испортить вёрстку:**

| Риск | Чем закрыт |
| --- | --- |
| Дата в чужом формате | Календарь вместо текстового поля + `check (start_date ~ '^\d{2}\.\d{2}$')` в базе |
| Снимок с телефона на 4 МБ в первом экране | Сжатие в браузере до WebP 800×1200 ([compress-image.ts](src/lib/compress-image.ts)) + bucket принимает только `image/webp` до 1 МБ |
| Пустая секция «Результати учасниць» | Последнюю карточку удалить нельзя; при пустой таблице сборка берёт запасной контент |
| Supabase недоступен при сборке | `sync-content.mjs` не падает — берёт [content.defaults.json](src/lib/content.defaults.json), он в гите вместе с фото |
| Двойное нажатие «Опублікувати» = двойная сборка | Пауза 3 минуты в `publish-site` |

**Кто может зайти.** Политики RLS выписаны только для роли `authenticated`, политик для `anon` нет вообще — без входа страница пустая, база не отдаёт ни строки и не принимает ни записи. Регистрация в Supabase выключена, аккаунт заводится вручную в дашборде. Прятать адрес `/admin` смысла нет — защищает не она, а база; `noindex` и `robots.txt` стоят только чтобы страница не лезла в поиск.

**Тихая поломка, которую стоит знать.** Если `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` в Netlify заскоплены только на **Functions**, сборка молча возьмёт запасной контент — сайт соберётся, будет выглядеть нормально и просто никогда не покажет правки Марины. В логе сборки это видно строкой `[content] беремо запасний контент`.

## Где остановились — работа поставлена на паузу 25.07.2026, возврат 08.08.2026

### Что работает и проверено живыми платежами

Оплата, проверка подписи, выдача одноразового инвайта, письмо, отклонение платежа, возврат денег и гашение инвайта при возврате. Тестовые платежи возвращены, база чистая. Инфраструктура на аккаунтах **Марины**, не разработчика: Netlify (`marinekfit` / сайт `marinek`), Supabase (проект `marinek-store`, ref `cdkexaplxybsldondifk`), Resend с подтверждённым доменом, бот в Telegram.

### Открытые хвосты — с них начинать

**1. Старые статичные инвайты в каналах — проверить, что отозваны.** Это главный незакрытый пункт: пока ссылки `+GOuTJufFE8g0MTVi` (Стандарт) и `+NNvTmwwDb1YzZmNi` (VIP) живы, в каналы пускают бесплатно, и половина смысла переделки теряется. Марина сказала, что отозвала, но **программно это не проверяется**: у бота нет метода для чужих ссылок, а страница `t.me` отдаёт одинаковый ответ и для живой, и для мёртвой, и даже для выдуманной. Единственная надёжная проверка — открыть ссылку с аккаунта, которого нет в канале.

**2. Возврат на страницу после оплаты НЕ РАБОТАЕТ. Три попытки, три промаха — четвёртую вслепую не делать.**

Что перепробовали:
1. `returnUrl` прямо на `/thank-you?t=…` → пустая 404 от Netlify (POST к статике)
2. `returnUrl` на функцию с `?t=…` → наша карточка «не знайдено», токен потерян
3. `returnUrl` на функцию с токеном **в пути** `/api/payment-return/<токен>` → снова «не знайдено»

Третий вариант на проде проверен curl-ом для POST без тела, GET и запасного поиска по `orderReference` — все три отдают ссылку. То есть **код работает, а живой возврат от WayForPay до него не доходит либо приходит без опознавательных данных**.

Диагностировать нечем: логи функций Netlify через CLI приходят с пустым сообщением, а каждая гипотеза стоит реального платежа.

**Следующий шаг — не очередная догадка, а вопрос в поддержку WayForPay:** каким методом и с какими данными они обращаются к `returnUrl` для аккаунта типа `freelance_user_`, сохраняют ли путь и query. Их документация про это молчит, проверено. Письмо **отправлено 03.08.2026**, ждём ответа. Пока его нет — **считать основным каналом выдачи письмо** (оно работает надёжно), а страницу оставить как есть: она уже показывает осмысленное сообщение с подсказкой про почту и контактом вместо голой ошибки.

Ещё вариант на проверку: возможно, для этого типа аккаунта `returnUrl` вообще игнорируется и WayForPay всегда показывает свою страницу результата. Тогда правильное решение — не чинить возврат, а убрать из воронки ожидание, что человек попадёт на наш сайт.

**3. Минуты сборки Netlify исчерпаны** (300/мес на бесплатном тарифе). Коммит `2686862` с кнопками «вернуться назад» на экранах ошибки собран локально, но не выкачен. Квота сбрасывается в дату биллингового цикла. Собирать реже: не делать `netlify deploy --build` на каждую гипотезу.

**4. Этап 2 — админка `/admin`, написана 12.08.2026, ждёт разовых настроек.** Задача переопределена заказчицей 03.08.2026: **таблицы заказов не будет** — платежи Марина смотрит в кабинете WayForPay, дублировать их незачем. Сделан редактор контента: дата старта (календарём) и карточки «Результати учасниць» (пары до/после, сжатие фото в браузере). Подробно — в разделе «Админка» ниже.

Не делалось, хотя обсуждалось:
- замена главного фото — тем же механизмом добавляется за полчаса, но в задании этой сессии не было;
- поиск заказа по e-mail и кнопка «Видати доступ повторно» — UI к уже написанной [reissue-invite](netlify/functions/reissue-invite.ts). Единственный сценарий, где админка нужна по заказам: WayForPay показывает платёж, но не знает, выдался ли инвайт в Telegram. Частично закрыто формой «надіслати лист ще раз» на `/thank-you`, которой женщина пользуется сама.

**5. ~~`/payment-failed` осиротела~~ — закрыто 04.08.2026.** Теперь на неё ведёт `payment-return`, когда отказ удалось распознать. Комментарий про несуществующий `declinedUrl` в файле поправлен.

**6. Адрес ФОП в футере на каждой странице.** Марина просила убрать; решили не трогать, потому что закон «Про електронну комерцію» (ст. 7) требует доступа к местонахождению продавца, и эквайер обычно тоже. Компромисс, если вернётся к этому: оставить только в оферте, из футера убрать — доступ сохранится, а из поисковой выдачи почти уйдёт.

### Прочее, не связанное с оплатой

- `/privacy` и `/rules` — черновики (оригинальные дизайн-файлы повреждены при передаче); заменить контентом 1:1 после восстановления оригиналов.
- Проверить соответствие фото ↔ имён в секции «Результати учасниць». Теперь это правится в `/admin`, а не в коде — задачу можно отдать Марине, она этих женщин знает.
- Апгрейд тарифа не предусмотрен: чтобы перейти со Стандарта в VIP, нужна вторая полная оплата. Пока разруливается вручную.
