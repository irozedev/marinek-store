# Кабінет `/admin` — разові налаштування

Код уже в репозиторії, але сам собою кабінет не запрацює: потрібні
таблиці, акаунт і адреса build hook. Нижче — п'ять кроків, кожен
робиться один раз.

Усе робиться **на акаунтах Марини** (Supabase `marinek-store`,
ref `cdkexaplxybsldondifk`; Netlify team `marinekfit`, сайт `marinek`).

---

> **Усе нижче вже зроблено 12.08.2026** — кабінет працює, перевірений
> живою публікацією. Ця сторінка лишається як опис того, з чого він
> складається: знадобиться, якщо доведеться заводити другого
> адміністратора, піднімати проєкт з нуля або розбиратися, чому щось
> перестало пускати.
>
> **Порядок має значення:** спершу акаунт, потім міграція. Міграція в
> останньому кроці шукає акаунт за поштою, щоб видати йому доступ, —
> якщо акаунта ще немає, вона свідомо впаде з поясненням.

## 1. Завести акаунт Марині

Supabase → **Authentication → Users → Add user → Create new user**:

- пошта — та, якою вона реально користується;
- пароль — згенерувати довгий і передати їй у месенджері, не в пошті;
- обов'язково поставити **Auto Confirm User**, інакше вхід не спрацює:
  листи підтвердження нікуди не підуть, бо власний SMTP не підключений.

З тієї ж причини **немає кнопки «Забули пароль?»**. Якщо пароль
загубиться — скинути його тут же, у дашборді, тим же способом.

## 2. Накотити таблиці

Supabase → **SQL Editor** → вставити вміст [db/002_content.sql](../db/002_content.sql).

**Перед Run замінити `ЗАМІНИТИ_НА_ПОШТУ_МАРИНИ`** на пошту з кроку 1 —
саме цей рядок і видає їй доступ. Якщо пошту не замінити або помилитись
у ній, запит впаде з поясненням: мовчазний провал тут гірший за помилку,
бо кабінет потім просто не відкриється й буде незрозуміло чому.

Файл написаний так, що його не страшно виконати двічі.

Перевірка: у **Table Editor** з'явилися `site_content` (один рядок,
`start_date = 03.08`), порожня `results` і `admins` з одним рядком;
у **Storage** — приватний bucket `results`.

## 3. Закрити реєстрацію

Supabase → **Authentication → Sign In / Providers → Email** →
вимкнути **Allow new users to sign up**.

Це вже не несуча стіна, а друга стіна за першою. Право редагувати дає
не факт входу, а рядок у таблиці `admins`: навіть якщо реєстрацію
колись увімкнуть, новий акаунт не побачить і не змінить нічого.
Спочатку політики RLS були виписані просто для ролі `authenticated` —
тоді весь захист кабінету тримався б на цьому перемикачі, і достатньо
було б одного необережного кліка в дашборді.

## 4. Створити build hook і покласти його адресу в env

Netlify → сайт `marinek` → **Site configuration → Build & deploy →
Build hooks → Add build hook**. Назва будь-яка («Кабінет Марини»),
гілка — `main`.

Скопійовану адресу додати як змінну оточення:

```
NETLIFY_BUILD_HOOK_URL=https://api.netlify.com/build_hooks/<id>
```

**Без префікса `NEXT_PUBLIC_`.** Ця адреса — і є право запустити збірку:
хто її знає, той може запускати їх скільки завгодно, а безкоштовний тариф
дає 300 хвилин збірки на місяць. У клієнтському бандлі вона була б видна
будь-кому у вихідному коді сторінки.

## 5. Перевірити, що збірка бачить базу

Netlify → **Environment variables** → у `SUPABASE_URL` і
`SUPABASE_SERVICE_ROLE_KEY` перевірити **Scopes**: має бути ввімкнено
не лише **Functions**, а й **Builds**.

Це найтихіша можлива поломка з усіх тут. Якщо ці змінні доступні лише
функціям, збірка мовчки візьме запасний контент із
`src/lib/content.defaults.json` — сайт зібереться, виглядатиме
нормально, і просто ніколи не покаже нічого з того, що Марина
відредагувала. У логах збірки це видно рядком:

```
[content] беремо запасний контент із content.defaults.json
```

Якщо все гаразд, там натомість буде:

```
[content] старт 03.08, карток результатів: 5
```

## Як це працює далі

```
Марина в /admin  →  правки лягають у Supabase (сайт не змінився)
       ↓ кнопка «Опублікувати»
/api/publish-site  →  перевіряє її токен  →  build hook
       ↓
збірка Netlify: scripts/sync-content.mjs забирає з бази дату й фото,
                кладе фото в public/uploads, далі звичайний next build
       ↓
новий статичний сайт
```

Правки **не потрапляють на сайт одразу** — і це навмисно. Можна спокійно
поміняти дату, додати кілька карток, передумати, щось видалити, і лише
потім показати все разом однією кнопкою. Доки не натиснуто
«Опублікувати», зламати живий сайт з кабінету неможливо в принципі.

## Що варто знати про це в роботі

**Збірка бере код із гіта, а не з ноутбука.** Кабінет запускає звичайну
збірку Netlify з гілки `main`. Тому все, що зроблено локально, має бути
запушене — інакше публікація Марини поверне сайт до стану останнього
коміту.

**Кожна публікація витрачає хвилини збірки.** Одна збірка — близько
2–3 хвилин із 300 на місяць. Пауза в 3 хвилини між публікаціями стоїть
у [publish-site.ts](../netlify/functions/publish-site.ts) саме тому:
подвійне натискання не має коштувати подвійної збірки.

**`[skip netlify]` кнопку з кабінету не глушить** — перевірено живою
публікацією 12.08.2026: збірка «Deploy triggered by hook: Кабінет
Марини» пішла попри `[skip netlify]` в останньому коміті. Прапорець
діє лише на збірки, які запускає пуш у гіт.
